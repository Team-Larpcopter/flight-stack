# Contributing to flight-stack

This repository holds first-party ROS 2 packages for Larpcopter flight software
(`flight_stack_ws` as a local checkout name).

## Pull requests

1. Branch off `main` with `{your-name}/{feature}` (example:
   `tommy/add-mission-state`). For LLM-authored work, prefer
   `{assistant}/{feature}` (example: `codex/flight-executive-node`) so those PRs
   are easy to spot.
2. Open a PR against `main`. Aim for at least one reviewer before merge
   (branch protection may not enforce this).
3. If the change is mostly generated by Codex/Claude (or similar), add the
   `codex/claude` label and leave self-review comments on GitHub. Re-read the
   diff yourself before asking others to.
4. Split complex work into multiple focused PRs. Smaller diffs review faster.
5. Keep multiple commits during review if that helps. Before merge, squash
   manually into a clean history (for example `git reset --soft` then one
   commit) when that fits the change.
6. Prefer **Rebase and merge**, not merge commits or GitHub’s squash-merge, so
   history stays linear.

Fill out the GitHub PR template (reason, description, verification). Verification
should say what you ran — for package changes that usually means a `colcon`
build and a short `ros2 run` / test smoke in a ROS 2 Humble environment. See
[docs/workspace.md](docs/workspace.md).

## Code layout

- Put ROS packages under `src/`.
- Declare runtime and test dependencies in each package’s `package.xml` /
  `setup.py` (or equivalent).
- Do not commit `build/`, `install/`, `log/`, credentials, bags, or local
  caches. Keep `.gitignore` current.

## Safety

Treat arming, offboard vehicle command, payloads, and real-vehicle operation as
out of scope unless the task explicitly expands that safety contract. Prefer
recorded-data and bounded runtime checks first.
